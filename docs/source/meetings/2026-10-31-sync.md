# Sync — design in chat, 2026-10-31

The owner and Claude, from scratch, one question at a time, with an architecture page, an animation, and arrays in chat ("let deviceA = [1, 2, 3]"). The whole design, explained start to end, is `docs/sync/index.html`; this is how it was reached. Sync stays build step 4, parked: decisions only.

## Research first

Searched: cr-sqlite (CRDTs in SQLite; maintenance unclear, 2.5× slower writes), SQLite's session extension (changesets, conflict handler, rebaser), Evolu (end-to-end encrypted, a relay that sees only timestamps), Replicache and Zero (server-decided, needs a server that reads the data), Apple CloudKit (key loss means data loss), Automerge with Keyhive (research-grade, group keys). The system's `libsqlite3` already has the session, changeset and rebaser functions; `lugha-sqlite` doesn't bind them.

## Goals before mechanics — settled (DECISION-068)

The owner got lost in mechanics ("simply answer what do we want"). Six goals: everywhere; with or without the internet (the owner: "it should work with or without the internet"); nothing lost; private; free for apps; no server required.

## Three devices — settled

The owner asked to see three devices, then to start "from a blank state where no device has the changes of the other". Devices are peers; the server only stores and forwards. A device numbers its own changes (A1, A2…); meeting means: say what you have (the highest number per device), send what's missing, merge. Changes hop: C gets B's changes through A and the server without meeting B.

## Merging, the clock, deletes — settled (DECISION-011, 069, 070)

Shown as steps with a task's title and done fields. Latest time wins per field, silently, losing changes kept (the owner: "a"). A slow clock would undo a later correction: a hybrid logical clock, a 5-minute guard for fast clocks (the owner: "just use your best judgement"). A delete wins over edits made without knowing about it; re-creating after seeing it brings the row back (the owner: "yes").

## Rules for apps — settled (DECISION-071, 072, 073)

Two offline devices both make note 5 and merge into one mixed-up note: random ids chosen by the app. Every table syncs but `local_` ones. No UNIQUE, FOREIGN KEY or CHECK in synced tables: two "work" tags would refuse each other forever.

## App versions — settled (DECISION-074)

The owner raised it ("still left is devices having different versions"), chose "option 1 and option 3": sync only on one version; the older device gets the newer one. Asked whether migrations could handle late edits: they can't, they've already run; add-and-copy instead of renames, and changes for unknown columns kept, not applied. Asked "won't this make tables with so many columns": few, cheap, droppable later. Asked whether the server would carry apps: no, it never does.

## Devices and networks — direction (DECISION-075, 076)

Pairing with matching codes (no camera), 12 recovery words, a sync key separate from the master secret. Mutual TLS against the signed device list; announcements with a changing tag. The owner asked about phones: the design holds; phones lean on the server more. Gaps: UDP in `std.net`, client certificates and pinning in `std.tls`.

## The Pond — settled (core decision 29, DECISION-077)

The owner: "should we really call it relay… rapidkoi the org can run the default one while users can host the same". Named to play on koi: the Pond, `./main pond`. Five rules: optional, can't read, one open protocol, no accounts, learns little. Then trimming the log: kept until everyone has a change; a device away 90 days starts fresh.
