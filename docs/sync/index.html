Sync in Rapidkoi

How every app's data stays the same across a person's devices, with or without the internet, without the app doing anything and without anyone else being able to read it.

Designed 2026-10-31 · not built yet (build step 4) · every rule here is a decision in DECISIONS.md

1What sync is for

Everything below exists to meet these six goals. When a choice was hard, it was settled by asking which goal it served. DECISION-068

  • 1EverywhereEvery app's data is on all of a person's devices.
  • 2With or without the internetDevices that can reach each other sync directly; apart, they sync across the internet.
  • 3Nothing lostDevices that changed things apart end up the same, and no change silently disappears.
  • 4PrivateOnly the person's own devices can read it. Anything in between sees sealed data.
  • 5Free for appsApps keep writing to their database. Rapidkoi does the syncing.
  • 6No server requiredThe Pond helps across the internet; without it, local sync still works.

2The parts

Each device keeps the full database of every app and works offline. Devices on the same network swap directly; apart, they swap through the Pond.

PartHolds or seesNever sees
The appIts own rows, plainThe log, clocks, keys, other devices, the Pond
app.dbThe app's tables: the current value of every field—
The sync logEvery change ever made: row, field, value, time, device, numberHidden from the app

A change is born when the app runs a write batch: Rapidkoi runs it in one transaction, and SQLite's session extension records what changed. Each changed field becomes a log entry, numbered per device (A1, A2, …). Open windows of the app get on_change when changes from elsewhere are merged.

3The conversation

Whenever two meet, whether two devices on the same Wi-Fi or a device and the Pond, they do the same three things:

  1. Say what you have. Not the changes themselves: the highest number from each device, like "A3 B0 C1".
  2. Send what's missing. Only the changes the other's summary lacks.
  3. Merge what arrives.

4Merging

A change says which field of which row became what, and when. When two changes touch the same field, the latest time wins, silently. Equal times are settled by the device, the same way everywhere. Different fields never fight. DECISION-011

DevicetitledoneIts log
  • Order doesn't matter. The rule looks only at times, so changes can arrive in any order and devices still agree.
  • Nothing leaves the log. Losing changes (struck through above) stay, so history (build step 6) can show and restore them.
  • Ruled out: the last write winning the whole row (it would drop B's tick), asking the person to pick, deleting a losing change.

5The clock

"Latest time" is only as good as the clock. A device whose clock is slow would make its new edits look old. The fix: each device remembers the latest time it has seen, and stamps a new change with the later of its own clock and that time, plus a tick. This is a hybrid logical clock. DECISION-069

  • Edits made apart, neither seeing the other, keep their devices' times. Either winning is acceptable, and both stay in the log.
  • A clock too fast would win every conflict and drag every device's clock forward. So a change stamped more than 5 minutes ahead of a device's clock waits in the log, unapplied, until the clock catches up.
  • The device with the wrong clock says so, in one short notice, when other devices' changes look far off to it.

6Deletes

A deletes task 7 at 10:05. B, apart and not knowing, ticks it done at 10:10. By time alone, B's tick would bring the task back, and deleted things would keep reappearing as devices come online. DECISION-070

A2: task 7 deleted,      10:05
B1: task 7 done = yes,   10:10    ← made without knowing about A2
→ task 7 stays deleted everywhere; B1 stays in the log

C receives A2 (task 7 is gone on C)
C1: task 7 created again, 10:20   ← made after seeing the delete
→ task 7 is back everywhere
  • A delete wins over edits made by a device that hadn't seen it, whatever their times.
  • A re-creation after seeing the delete brings the row back: that's deliberate.
  • The delete stays in the log, so a device that was away learns the row is gone instead of sending it back.

7Rules for apps

Apps write ordinary SQL. Three rules on their tables, all part of contract 8, keep merges safe. Rapidkoi checks a table's definition when the app creates it, and tells the developer in a sentence when a table won't sync.

Random ids, chosen by the app DECISION-071

SQLite numbers rows as the highest so far plus one. Two devices apart would both make note 5, and merging field by field would blend two notes into one:

A: note 5  title "Shopping" (10:00)  body "milk, eggs" (10:00)
B: note 5  title "Ideas"    (10:01)  body "a sync animation" (09:59)
merged → note 5 = title "Ideas", body "milk, eggs"     ← two notes became one

So rows in synced tables get random, time-ordered ids the app chooses (rapidkoi-rust gains a helper). A row has the same id on every device, so links work everywhere. Renumbering behind the app's back is ruled out: it would break links.

Every table syncs, except local_ ones DECISION-072

A table whose name starts with local_ stays on its device: a cache, a draft kept here, "last opened on this device". It may number rows the SQLite way.

No rules a merge can break DECISION-073

A synced table may have no UNIQUE (besides its id), no FOREIGN KEY, no CHECK. Two devices each making a tag "work" would otherwise refuse each other's row and never match. The app handles what a merge can leave in what it shows: two tags of one name the person can combine, an item whose list is gone. local_ tables keep every rule.

8App versions

A upgrades Notes, whose new version adds a column. B, offline, still runs the old one. DECISION-074

  • Two devices sync an app only when both run the same version of it.
  • The older device catches up: from the app's site, as kept apps update; with no internet, from a device on the same network that has it, checked exactly as from the site.
  • The Pond never carries apps: it mustn't learn which apps a person uses, and a device that reaches the Pond can reach the app's site.
  • Open windows aren't swapped: the new version starts at the next open or when the person upgrades, and that app syncs from then.
  • An app that can't upgrade (withdrawn, or its publisher's key changed) doesn't sync between those devices, and the person is told once.
  • A change for a column or table a device doesn't have is kept, not applied. That covers edits made on an old version arriving after an upgrade.
For developers: add columns, never rename. To rename, add the new column and copy into it. Drop an old column in a later version whenever you like: late edits to it are kept in the log and ignored. Never reuse an old name for something new.

9Meeting on a network

How two of a person's devices on the same Wi-Fi find each other and talk, with no internet. DECISION-076

  • Proving who you are is mutual TLS: each side's device key checked against the signed device list, encrypted by OpenSSL, as Syncthing does.
  • Announcements go out on every network, carrying a tag that looks random to strangers and changes. One switch, "Sync over local networks", turns it off.
  • Remembered addresses: each device tries where it last reached each of the others first. Quicker, and works where announcements are blocked.

10Adding a device

Each app's key for the person is derived from the device's master secret, so a new device needs the same master secret to be the same person in every app. DECISION-075

A device holdsShared?For
Master secretSame on allThe same person in every app
Sync keySame on allSealing changes; renewed when a device is removed
Device keyIts ownProving which device it is, signing its changes
Device listSame on all, signedWhich devices are the person's

Pairing, every day

  1. On the new device, Add this device. It meets a device already set up, on the Wi-Fi or through the Pond.
  2. They set up an encrypted connection, and both show the same short code worked out from it.
  3. The person checks the codes match and approves on the old device. A device in the middle would make the codes differ.
  4. The old device sends the master secret, the sync key and the list. No camera or internet needed.

Recovery words, when no other device is left

Shown once when sync is first turned on: 12 words that are the master secret. Typed on a new device, they give it the master secret; it then fetches the sync key and the list, kept on the Pond sealed with the master secret. Anyone with the words is the person, in every app.

Removing a device

From any remaining device. The others make a new sync key and drop it from the list, so it reads nothing sent after. Weak spot: it still has the master secret and can still sign in to apps as the person; that's an identity question (DECISION-022), not sync's.

The person's own Rapidkoi settings sync too (per app: Start over, signed out, the name), or one person would look different in an app on another device.

11The Pond

Rapidkoi's server. Rapidkoi runs the default one; anyone can run the same software with ./main pond and point their devices at it. Switching is changing an address. core decision 29

  1. Optional. Everything works without a pond, in a reduced form.
  2. It can't read anything. The default pond can't read your data any more than your own can.
  3. One open protocol, the same software. A device can move its sealed data from one pond to another with no loss.
  4. No accounts. Devices prove themselves with their keys.
  5. It learns as little as possible: who syncs, how much and when. Your own pond removes even that from Rapidkoi's view.

Sync is its first use. Later candidates, each decided on its own: recovery, waking phones, live sessions, web links.

12Trimming the log

The log catches devices up, keeps deletes until everyone has seen them, and holds history. DECISION-077

  • Every change is kept until every device on the list, and the Pond, has it. The summaries say when.
  • The Pond then drops it. Devices keep a sealed copy of the current data there, so a new or recovering device starts from it.
  • A device not seen for 90 days isn't waited for. When it returns it starts from a fresh copy and sends what it made while away.
  • History stays within a cap, 100 MB per app's log, oldest first, until history (build step 6) decides how long.

13Phones

The design treats a phone as any other device. Rapidkoi doesn't run on phones yet (Android first, iOS uncertain). Phones pause apps in the background, so a phone syncs while Rapidkoi is open, when the system lets it run briefly, or when woken through a push service, which needs a server and stays optional. Nothing in sync assumes a device can stay online or listen all the time.

14Building it

Sync stays build step 4, parked by the owner. When it's built, it needs:

  • Upstream, each fixed in its own repository: session and changeset bindings in lugha-sqlite; UDP and multicast in std.net; client certificates and pinning in std.tls.
  • Contract 8: random ids, local_ tables, no merge-breakable rules in synced tables.
  • Elsewhere: the id helper in rapidkoi-rust; Notes moving to random ids.
  • The owner's review: all cryptography (pairing, keys, recovery words, TLS) and passing app bundles between devices.
  • A PRP, and the owner un-parking step 4.
